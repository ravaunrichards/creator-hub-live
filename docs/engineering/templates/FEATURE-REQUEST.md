# Feature request

## User problem
Who is affected, and what are they trying to accomplish?

## Current behavior and evidence
Route/page, user state, device/browser, repeatable steps, relevant logs/screenshots (redacted). State what is observed separately from assumptions.

## Desired outcome
Describe what the user should be able to do without prescribing an implementation too early.

## Acceptance criteria
- [ ] Primary success path
- [ ] Loading/empty/error/retry behavior
- [ ] Unauthorized/blocked/private-state behavior
- [ ] Mobile/responsive/Android WebView behavior where relevant
- [ ] Real persistence and refresh/reload behavior where relevant

## Scope boundaries
What is explicitly in scope? What should not change? Which existing working behaviors must be preserved?

## Data and security impact
New tables/columns/functions/policies? Personal data or retention? Auth/role checks? Logs/metrics? Payment/gift/diamond/wallet impact? External provider or API terms?

## Verification plan
Exact automated commands, manual paths, actor roles, devices, and safe test accounts.

## Risk, rollout and recovery
Risk class (R0-R3), dependency order, feature flag/gradual exposure if appropriate, backup/rollback/compensation, owner, required approval.

## Decision
Proposed / Accepted / Rejected / Blocked — rationale and owner.
